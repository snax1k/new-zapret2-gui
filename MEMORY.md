# MEMORY.md — рабочая память проекта

Сжатая выжимка всего, что выяснено про Zapret2 Control Center и ядро zapret:
правила, нарушение которых ломает программу, разобранные баги с их настоящими
причинами, смысл каждого параметра в пресете и список нерешённого.

Читать перед любой правкой стратегии обхода или командной строки. Общее
описание проекта и инструкции по сборке — в [README.md](README.md).

Актуально на **v0.3.0** (2026-09-21), ядро **zapret v72.13**.
Руководство пользователя — [docs/user-guide/](docs/user-guide/): `guide.html`
как исходник, PDF на 21 страницу как результат, порядок пересборки и правила
пересъёмки экранов в `docs/user-guide/README.md`.

## 1. Правила ядра, которые нельзя нарушать

Всё проверено по исходникам в `zapret-raw/zapret-v72.13/`. Нарушение первых
трёх пунктов ядро не прощает: либо мгновенный выход с кодом 1, либо тихая
неработа.

| Правило | Что будет при нарушении |
|---|---|
| Обязателен `--wf-tcp` / `--wf-udp` / `--wf-raw`. `--filter-tcp`/`--filter-udp` — это фильтр **профиля**, он НЕ заменяет `--wf-*` | `windivert filter : must specify port or/and partial raw filter`, выход 1 |
| `--dpi-desync-autottl` принимает только `[+-]<delta>[:<min>[-<max>]]` (`nfqws.c:804`) | `dpi-desync-autottl value error`, выход 1 |
| Путь в `--ipset` проверяется через `stat()` на разборе аргументов (`ipset.c:266`) | `cannot access ipset file`, выход 1. У `--hostlist` такая же проверка **закомментирована**, поэтому битый хостлист падения не даёт |
| Порядок профилей: `dp_find`/`dp_match` в `desync.c` выбирает **первый** подходящий | Профиль перехватит трафик, предназначенный следующему |
| «Профиль не может выиграть, если заданы обычные хостлисты без auto-hostlist, а имя хоста неизвестно» (`dp_match`) | Профили с `--hostlist` никогда не сработают для MTProto и прочего трафика без SNI |
| `seqovl` для `split`/`multisplit` — только абсолютное число; маркеры вида `midsld-1` допустимы лишь для `disorder` (`readme.md:556`) | seqovl молча отменяется |
| Первый сегмент вместе с `seqovl` не должен превышать MTU. На Linux это ловится и seqovl отменяется, **на Windows — нет** (`readme.md:537`) | Соединение рвётся |
| `--dpi-desync-any-protocol` без `--dpi-desync-cutoff` | Ядро само предупреждает; рвутся длинные соединения |
| Относительные пути вида `../host-list/файл` для winws не работают | См. баг v0.0.5 в §3. Всегда абсолютные пути |

### Мелочи, которые уже стоили времени

* Дефолтный фейк для `discord`/`stun`/`wg`/`dht`/`unknown-udp` — **64 нулевых
  байта** (`params.c:272-280`, ветка `fakes_z64`). Специально безобидный.
* `IsDiscordIpDiscoveryRequest` (`protocol.c:1026`) срабатывает **только** на
  пакете длиной ровно 74 байта. Значит `--filter-l7=discord,stun` трогает
  установку соединения, а не голосовой поток.
* Без `--dpi-desync-ttl` / `--dpi-desync-autottl` фейк уходит с TTL оригинала,
  то есть **долетает до сервера назначения**.
* `--dpi-desync-split-seqovl-pattern` заполняется повтором файла
  (`fill_pattern`), поэтому паттерн короче запрошенного seqovl — не ошибка,
  но получается обрезанная TLS-запись.
* `MAX_SPLITS = 64` (`params.h:56`) — позиций в `--dpi-desync-split-pos` может
  быть много.
* Маркеры позиций: `host`, `endhost`, `sld`, `midsld`, `endsld`, `sniext`
  (`protocol.c:74-80`). Виды fooling: `none`, `md5sig`, `ts`, `badseq`,
  `badsum`, `datanoack`, `hopbyhop`, `hopbyhop2` (`nfqws.c:1273-1285`).
  Режимы десинхронизации: `multisplit`, `multidisorder`, `fake`, `fakedsplit`,
  `fakeddisorder` (`desync.c:203-209`).

### Как работают хостлисты (`hostlist.c`)

* Сначала проверяется exclude, и он **побеждает**.
* Пустой include-набор = проходит всё.
* Поддомены матчатся отбрасыванием левых меток:
  `www.youtube.com` → `youtube.com` → `com`.
* `^` в начале строки — строгое совпадение. `#`, `;`, `/` — комментарии.
  gzip поддерживается.
* Файлы **перечитываются по mtime** — ядро подхватывает правки без перезапуска.
  Приложение этим пока не пользуется: `list-user.txt` пишется только перед
  стартом ядра.

## 2. Текущая стратегия (единственный пресет `general-v72`)

`--wf-tcp=80,443,2053,2083,2087,2096,8443`,
`--wf-udp=443,19294-19344,50000-65535`.
Шесть профилей через `--new`. **Порядок менять нельзя.**

| # | Назначение | Ключевые параметры и зачем |
|---|---|---|
| 1 | QUIC / HTTP-3 | `--filter-udp=443` + списки, `--dpi-desync=fake --dpi-desync-repeats=6 --dpi-desync-fake-quic=quic_initial_www_google_com.bin` |
| 2 | Голос Discord | `--filter-udp=19294-19344,50000-65535 --filter-l7=discord,stun --dpi-desync=fake --dpi-desync-repeats=6`. Диапазон `19294-19344` обязателен — без него часть комнат молча остаётся без звука. **Фейк не задаётся намеренно**, см. баг v0.0.7 |
| 3 | Медиасерверы Discord | `--filter-tcp=2053,2083,2087,2096,8443 --hostlist-domains=discord.media`, multisplit pos=1 seqovl=681 |
| 4 | YouTube и Google | `--filter-tcp=443 --hostlist=list-google.txt --ip-id=zero` + стратегия из §5. `--ip-id=zero` не косметика: по `readme.md`, на ТСПУ повторение ненулевых ip_id у фейка и не-фейка триггерит блок на диапазонах `googlevideo.com` |
| 5 | Остальные сайты | `--filter-tcp=80,443` + списки, multisplit pos=1 seqovl=568 |
| 6 | Telegram | `--filter-tcp=80,443 --ipset=ipset-telegram.txt --dpi-desync-any-protocol=1 --dpi-desync-cutoff=n3`. **Обязан быть последним**: у MTProto нет имени хоста, отбор только по подсетям. `cutoff=n3` ограничивает вмешательство первыми пакетами — без него рвётся загрузка медиа |

Сборка команды целиком живёт в [`src/lib/zapretCommand.ts`](src/lib/zapretCommand.ts):
разбор на профили по `--new`, отсев отключённых переключателями, дедупликация
опций внутри профиля (со списком повторяемых: `--hostlist`,
`--hostlist-exclude`, `--ipset`, `--ipset-exclude`, `--wf-raw-part`,
`--dpi-desync-fake-tls`, `--dpi-desync-fake-quic`) и вывод `--wf-*` из портов
выживших профилей.

Расхождения с эталонным `general.bat` из Flowseal/zapret-discord-youtube:
у нас нет их собственных `ACTIVE_DISCORD_UDP.bin`, `ACTIVE_GAME_UDP.bin`,
`tls_clienthello_4pda_to.bin` и `ipset-all.txt`, нет игровых профилей.
Профиль 5 поэтому использует 681-байтный паттерн, обрезанный до 568 —
у Flowseal там отдельный файл ровно на 568 байт.

## 3. Разобранные баги и их настоящие причины

### v0.0.2 — «ничего не работает» (три бага друг на друге)

1. **`--wf-*` не выводился никогда.** Условие было
   `if (!args.Contains("--wf-tcp") && !args.Contains("--filter-tcp"))`, а
   `--filter-tcp` есть в каждом пресете. Ядро не стартовало вообще.
2. **`--dpi-desync-autottl=auto:2:3-12`** — невалидный формат, выход 1.
3. **Интерфейс всегда показывал «подключено».** Не было ни проверки живучести,
   ни обработчика `Exited`, ни реального PID.

Починено: вывод `--wf-*` из портов профилей плюс страховка на стороне C#,
`normalizeAutoTtl` (срезает legacy-префикс `auto:`, валидирует, при ошибке
опция не добавляется), переписан `StartZapretProcess` с `WaitForExit(1500)`.

### v0.0.4 — Discord: во 2-й и 3-й комнате нет звука

Не хватало UDP-диапазона `19294-19344` — часть голосовых комнат выдаётся именно
на этих портах. Добавлен и в `--wf-udp`, и в профиль. Плюс отдельный профиль
`discord.media` на альтернативных TCP-портах Cloudflare.

### v0.0.4 — Telegram: медиа грузится бесконечно

У MTProto нет имени хоста, поэтому **ни один** профиль с хостлистом его не
поймает (правило `dp_match` из §1). Добавлен `ipset-telegram.txt` и профиль по
подсетям с `--dpi-desync-any-protocol=1 --dpi-desync-cutoff=n3`, поставлен
последним.

### v0.0.5 — регрессия: `cannot access ipset file '../host-list/ipset-telegram.txt'`

Внесена мной при переносе списков из `bin\` в отдельный `host-list\`.
Проверено: файл существовал, рабочий каталог был правильный, а `mdig.exe` из
той же cygwin-сборки такой относительный путь резолвил без проблем.
**Причина так и не установлена** — воспроизвести запуск ядра для отладки не
получилось, оно требует прав администратора.

Устранён сам класс проблемы: в пресете путь пишется маркером `{LISTS}/файл`,
`ResolveListPaths` в `NativeApp.cs` подставляет абсолютный путь в кавычках с
прямыми слешами. Работает и с пробелами, и с кириллицей в пути. Так же
устроено у Flowseal. Плюс добавлена предстартовая проверка наличия всех файлов
списков — вместо невнятного падения ядра с кодом 1.

### v0.0.7 — Discord: 5000 мс задержки при 0% потерь исходящих

Тоже моя ошибка. В профиль 2 я прописал
`--dpi-desync-fake-discord=quic_initial_www_google_com.bin` — **1200 байт
QUIC-пакета**, потому что у Flowseal там их собственный
`ACTIVE_DISCORD_UDP.bin`, которого у нас нет. С `--dpi-desync-repeats=6` и без
ограничения TTL шесть таких пакетов **долетали до голосового сервера** прямо
перед 74-байтным Voice IP Discovery.

Ровное «5000 мс» — не измеренный пинг, а потолок: пакеты уходят (0% потерь
исходящих), ответы не возвращаются, сигнальный канал жив, поэтому клиент рисует
«соединение установлено».

Починено удалением обеих опций — ядро подставляет свои 64 нулевых байта.
**Пользователь подтвердил, что Discord после этого работает идеально.**
Профили 2 и 3 трогать без крайней необходимости не стоит.

### v0.0.7 — исправления стратегии не доходили до пользователя

Встроенный пресет читался из localStorage целиком, поэтому любая правка
стратегии требовала сброса хранилища с потерей пользовательских пресетов.
Теперь встроенные пресеты всегда берутся из сборки, а пользовательские
(по id, которых нет в `INITIAL_PRESETS`) сохраняются.

### После 0.2.0 — Watchdog писал «очищено», не проверив ничего

`killZombieWinDivert` в `AppContext.tsx` отправляла `stop_engine` и через
`setTimeout(800)` безусловно печатала в журнал
«Все зависшие процессы очищены (taskkill /F /IM winws.exe выполнено)».

Два вранья в одной строке: `stop_engine` останавливает **своё** ядро, а не
чужие процессы, никакого `taskkill` не запускалось вообще; и результат никто
не проверял — строка печаталась по таймеру.

Починено отдельным сообщением `kill_stale_winws` → `KillStaleWinws()` в
`NativeApp.cs`. Метод берёт тот же список, что и пункт «Найдены посторонние
winws.exe» в `CollectPreflight` (`Process.GetProcessesByName("winws")` минус
свой PID), снимает найденное, **проверяет `HasExited`** и отвечает
`{"type":"stale_winws_done","found":N,"killed":M,...}`. Итоговую строку в
журнал пишет интерфейс по этим числам: сколько нашли, сколько сняли, либо
«посторонних процессов не найдено». Подробности по каждому PID — только в
`zapret2.log` через `WriteLogFile`. В конце вызывается `SendPreflight()`,
иначе пункт проверки окружения висел бы после успешной очистки.

Заодно `KillZombieWinDivert()` (снимает **все** winws, включая своё ядро —
старт, остановка, выход) возвращает число фактически завершённых, и подсказка
в трее показывает его вместо «Процессы winws успешно очищены».

Тот же класс, что плашка «100% УСПЕХ» в 0.1.3 и кнопка сворачивания в 0.1.4.
Правило: интерфейс не сообщает о том, чего не проверял.

### 0.2.0 — установка обновления не работала НИ РАЗУ (CORS)

Окно обновления показывало «в релизе нет файла SHA256SUMS.txt, проверить
сборку нечем» и отключало кнопку установки. Файл в релизе при этом лежал и
скачивался руками без вопросов.

**Причина.** Страница интерфейса живёт на `https://app.zapret` (виртуальный
хост WebView2), а ассеты релиза раздаются с хоста GitHub, который **не отдаёт
заголовки CORS**. `fetch` за `SHA256SUMS.txt` падал с `TypeError: Failed to
fetch`, переменная `sha` оставалась пустой, `canInstall` уходил в `false`.
При этом `api.github.com` CORS отдаёт — список ассетов приходил нормально, и
со стороны это выглядело как «файла нет в релизе».

Проверяется одной строкой в консоли страницы:

```js
await fetch('https://github.com/<owner>/<repo>/releases/download/<tag>/SHA256SUMS.txt')
// TypeError: Failed to fetch
```

**Сидело с 0.1.2.** В §8 честно стояло «осталось проверить полный путь
вживую» — стенд проверял только подмену файла, сети и сумм в нём не было.
Проверили через полтора месяца, когда пользователь нажал кнопку.

**Как чинится.** Качать файл сумм обязана нативная часть: `WebClient` про
CORS ничего не знает. Веб-слой передаёт в `download_update:` **ссылку** на
`SHA256SUMS.txt` вторым полем вместо самой суммы, нативный
`FetchSha256FromSums` её скачивает и достаёт 64 hex-символа по имени файла.
Ссылка проверяется тем же `IsTrustedUpdateUrl`, что и ссылка на сборку.

Сумма запрашивается **до** загрузки сборки: раньше файл качался целиком и
только потом выяснялось, что сверять не с чем.

Правило не ослаблено: без совпавшей суммы установка не выполняется.

**Чего почина не может.** В уже установленных 0.1.2–0.1.5 сидит прежний код,
и обновиться на 0.2.0 они по-прежнему не смогут — её ставят руками один раз.
Автообновление заработает начиная с 0.2.0.

Заодно: список «что включено в обновление» собирался построчно из описания
релиза и показывал тройные кавычки, линейки из «=» и обрывки предложений.
Теперь линейка считается границей абзаца, абзацы склеиваются, а из описания
берутся вступление и названия разделов (`parseReleaseHighlights`).

### 0.2.1 — правки встроенного пресета стирались при каждом запуске

Загрузчик пресетов всегда брал встроенный пресет из сборки, а сохранённую
копию выбрасывал:

```ts
const custom = stored.filter(p => !builtinIds.has(p.id));
return [...INITIAL_PRESETS, ...custom];
```

Сделано это было осознанно — чтобы исправления стратегий доезжали до тех, у
кого уже лежит сохранённая копия. Но цена оказалась выше задачи: **любая
правка пользователя во встроенном пресете молча исчезала при перезапуске**.
Пользователь описал это как «пресет не запоминается».

Чинится подписью эталона (`BUILTIN_SIGNATURE` — JSON из id и args всех
`INITIAL_PRESETS`), которая пишется в `zapret2_builtin_sig_v1` вместе с
пресетами:

* подпись совпала — сборка та же, значит всё расхождение внёс пользователь,
  и его версия встроенного пресета восстанавливается как есть;
* подпись не совпала — мы выпустили новый встроенный пресет. Ставим его
  (иначе исправления не дойдут), а правки не теряем: откладываем копией
  «<имя> (правки до обновления)» с новым id.

Проверено на обеих ветках: правка `multisplit → multidisorder` переживает
перезапуск, а при смене подписи появляется и свежий встроенный пресет, и
копия с правками.

### 0.2.1 — автоподбор мерил туннель вместо провайдера

`RunAutotune`, `TryTlsProbe` и диагностика открывали обычный `new TcpClient()`
и шли туда, куда ведёт таблица маршрутизации. Обойти системный прокси мало:
прокси — это настройка, её сокет и так игнорирует, **а туннельный адаптер
перехватывает трафик маршрутом**. У пользователя это `happ-default-tun`
(SocksTunnel) и Tailscale; `Find-NetRoute` к `162.159.128.233` уходил в
интерфейс 32.

Последствие хуже, чем «не поможет»: через туннель работает всё, и подбор
сообщил бы, что прошли все семь вариантов. Ровно та же ложь, что плашка
«100% УСПЕХ» в 0.1.3 и кнопка watchdog в 0.2.0.

Теперь сокет привязывается к адресу физической карты (`CreateProbeClient` →
`FindPhysicalLocalAddress`). Адаптер отбирается по трём признакам сразу:
настоящий MAC, отсутствие опознаваемого слова в описании (`tun`, `tap`,
`vpn`, `tailscale`, `wireguard`, `socks`, …) и наличие шлюза. Поодиночке ни
один не надёжен: WinTun-адаптеры представляются как Ethernet, а слово в
названии бывает у вполне физических карт. Не нашли — идём как раньше и
пишем об этом предупреждение.

Выбранный адрес пишется в журнал при каждом запуске подбора и диагностики.

**Как проверять руками** (это же годится для разбора чужих логов):

```powershell
$local = New-Object System.Net.IPEndPoint([System.Net.IPAddress]::Parse("<IP карты>"), 0)
$c = New-Object System.Net.Sockets.TcpClient($local)
```

Блокировка по имени сайта выглядит так: с настоящим SNI — тишина и обрыв
через ~19 с, с посторонним именем на тот же IP — ответ за 40 мс.

### 0.2.2 — настройки терялись при закрытии (асинхронный localStorage)

Пользователь: «меняю пресет, закрываю, открываю — прежний». Чинилось у него
удалением данных приложения, после чего какое-то время всё сохранялось.

**Причина не в пресетах.** localStorage в Chromium не пишется на диск сразу:
изменения копятся в памяти и коммитятся пачкой через несколько секунд
простоя либо при аккуратном закрытии движка. А `MainForm_FormClosing`
вызывал `Application.Exit()`, не тронув `webView`, — процесс
msedgewebview2.exe убивался вместе с нашим, и незакоммиченное пропадало.
Отсюда и «случайность»: поработал подольше — сохранилось, закрыл сразу —
нет.

Удаление данных ничего не чинило: база просто создавалась заново, первые
записи попадали в неё при старте (они успевают), и на несколько запусков
создавалось впечатление, что помогло. Каталоги `%APPDATA%\zapret-gui`,
`zapret2-gui`, `zapretui`, которые пользователь удалял, вообще от старых
сборок на Tauri — нынешнее приложение пишет только в `%LOCALAPPDATA%`.

**Как чинится.** Настройки больше не доверяются браузерному хранилищу:

* нативная часть держит их в `%LOCALAPPDATA%\Zapret2-GUI\settings.json`,
  пишет синхронно (`SaveSettingsJson`, запись во временный файл и
  `File.Replace` — сбой посреди записи не обнулит всё разом);
* на старте содержимое вкладывается в страницу через
  `AddScriptToExecuteOnDocumentCreatedAsync` ДО навигации, поэтому гонки
  «что прочитается раньше» нет;
* интерфейс ходит через `src/lib/settings.ts`: `loadSetting` предпочитает
  вложенное, `saveSetting` пишет и в localStorage, и в файл (пачкой через
  150 мс), `flushSettings` вызывается перед закрытием;
* значения крупнее 64 КБ в файл не едут — это про своё изображение фоном
  (data-URI на мегабайты). Оно остаётся только в localStorage: потерять
  фон не то же самое, что потерять все настройки.

Заодно `webView.Dispose()` перед выходом — чужие данные тоже не должны
пропадать молча.

**Проверено** в браузере на временно вложенном `window.__zapret_settings`:
вложенные значения перебивают localStorage (тема стала светлой, активный
пресет — подставленный), после чего записываются обратно.

**Правило на будущее: ничего важного не хранить в localStorage.** Он
асинхронный, и приложение не контролирует момент записи.

### 0.2.3 — файлы прошлых версий копились на диске

`ExtractResources` перезаписывала файлы по имени и **не удаляла ничего**.
Значит всё, что мы когда-либо поставляли и перестали, оставалось навсегда.

Главный накопитель — сборка интерфейса: имя содержит хэш содержимого
(`index-D2Ys9Scj.js`), поэтому каждая версия приносила новое имя, а прежнее
оставалось рядом. Полмегабайта на выпуск. Плюс списки, которые мы перестали
поставлять (`ipset-telegram.txt` после 0.1.5).

**Вес — не главное.** Ошибки распаковки проглатываются
(`try { entry.ExtractToFile(...); } catch { }`), и при занятом файле
получалась смесь версий: новый `index.html` со ссылкой на новый бандл и
старые `assets` рядом. Белое окно без единого сообщения.

Чинится маркером `unpacked-version.txt` в корне каталога данных:
`PurgePreviousVersion` сравнивает его с `AppVersion` и при расхождении сносит
`dist` и `bin` целиком (`PurgeDirectory`), после чего идёт обычная
распаковка. Маркер пишется **только если уборка прошла без остатка** — иначе
версия в нём останется прежней и попытка повторится при следующем запуске.

Уборка безопасна по времени: чужие winws снимаются в `Main` до создания
формы, поэтому к моменту сноса `bin\` никем не занят.

Не трогаются никогда: `host-list` (домены пользователя), `settings.json`,
`logs`, `WebViewData`.

## 5b. Системный прокси перекрывает обход — ГЛАВНОЕ

**На машине пользователя постоянно включён VPN INCY через системный прокси
Windows** (`HKCU\...\Internet Settings`, `ProxyEnable=1`,
`ProxyServer=127.0.0.1:10808`, слушает `incy.exe`). Через него идёт и связь с
Claude, выключать его нельзя.

Последствие принципиальное: приложения отправляют HTTP(S) не на адрес сайта,
а на `127.0.0.1`. Фильтр WinDivert начинается с `!impostor and !loopback`,
поэтому **winws такой трафик не видит вообще**. В логе будут нули, а
переключение стратегий не изменит ничего.

Разделение труда получается такое:

| Трафик | Кто обрабатывает |
|---|---|
| TCP 80/443 браузера, Discord, Telegram Desktop | **прокси INCY**, обход не участвует |
| UDP: голос Discord, QUIC | **обход**, через HTTP-прокси UDP не идёт |

Именно поэтому исправление фейкового пейлоада для голоса в v0.0.7 реально
помогло, а любые правки TCP-профилей на Discord не влияют никак.

**Как это диагностировать за минуту:**

```
powershell -ExecutionPolicy Bypass -File scripts\check_discord.ps1
```

Скрипт печатает состояние обхода, состояние системного прокси (включая то,
слушает ли кто-нибудь порт) и проверяет каждый эндпоинт Discord **двумя
путями** — напрямую и через прокси. Ранняя версия скрипта проверяла только
один путь и из-за этого дважды ввела в заблуждение.

Начиная с v0.0.9 приложение само пишет в лог предупреждение при старте ядра,
если системный прокси включён (`WarnIfSystemProxy` в `NativeApp.cs`).

**Практический вывод:** прежде чем разбирать пустой лог, проверьте прокси.
Симптом «Discord крутит Update failed — retrying in N sec» без единого пакета
в логе означает, что прокси-клиент в этот момент не отвечал, и обход тут
совершенно ни при чём.

## 5в. Инструменты самодиагностики (v0.1.0)

Три вещи, добавленные после того, как три круга подряд ушли на разбор пустых
логов. Стратегию обхода они не трогают.

### Карточка «Обработано»

Пятая карточка на главной. Считается разбором вывода ядра в
`CountActivity` (`NativeApp.cs`): строки `dpi desync src=` дают счётчик
вмешательств, строки `hostname: X` — множество распознанных хостов. Раз в
секунду `PushActivity` шлёт в интерфейс сообщение `{"type":"activity"}`, и
только если значения изменились.

Ноль при работающем ядре подсвечивается жёлтым — это ровно тот сигнал,
которого не хватало. **Важно:** ядро печатает эти строки только с `--debug`,
поэтому при выключенном «Подробном логе» карточка показывает «н/д», а не ноль.

### Проверка окружения

`CollectPreflight()` в `NativeApp.cs`, сообщение `{"type":"preflight"}`,
компонент `PreflightPanel.tsx`. Четыре проверки, каждая из реального случая:
системный прокси (см. §5b), поднятые TUN/TAP-адаптеры, посторонние
`winws.exe`, другой обходчик DPI. Запускается сама через 800 мс после старта
приложения и по кнопке.

### Автоподбор стратегии

`RunAutotune()` в `NativeApp.cs`, компонент `AutotuneModal.tsx`.
Перебирает все варианты кроме `off`, поднимая ядро с каждым, и проверяет
TCP + TLS с нужным SNI.

Два решения, которые нельзя ломать:

* проверка идёт через `TcpClient`/`SslStream` — **они системный прокси не
  используют**. Через `WebRequest`/`Invoke-WebRequest` проверялся бы прокси,
  а не обход (на этом уже обожглись, см. §5b);
* имена резолвятся **один раз до перебора**, дальше все варианты идут на один
  и тот же IP — иначе DNS становится ещё одной переменной.

Протокол IPC намеренно не JSON: `autotune:<restoreArgs>\x1f<hosts>\x1f<id|label|args>\x1e...`.
Аргументы winws содержат кавычки и слеши, и городить экранирование ради одного
сообщения смысла нет.

На время перебора `autotuneRunning` подавляет `SendStatus`, иначе кнопка
питания мигала бы «подключение → работает → остановлено» по разу на вариант.
В `finally` ядро возвращается к исходной стратегии (`restoreArgs`) или
остаётся выключенным.

## 5в-3. Автоподбор мерит результат, а не скорость (0.3.0)

Жалоба пользователя: «подобрал вариант с самым низким пингом, а он не
работает». Разбор показал три независимые причины, и все три были в коде.

**1. Победитель выбирался по времени.** В `AutotuneModal` стояло
`finished.filter(r => r.ok).sort((a, b) => a.ms - b.ms)`. Это неверно в
корне: быстрый ответ часто означает быстрый отказ. Живой замер 2026-09-21 на
канале пользователя: блокировка по SNI отвечала сбросом за **38 мс**,
успешное соединение занимало **300 мс**, а полная блокировка — 19 200 мс до
обрыва. Самое маленькое число было у неудачи.

Теперь сортировка по числу успешных проб, время — только разделитель при
равном счёте.

**2. Эталон в подборе не участвовал вовсе.** В `startAutotune` стояло
`YOUTUBE_STRATEGIES.filter(s => s.id !== 'off')`. То есть вопрос «а
блокируют ли здесь хоть что-нибудь» не задавался никогда: человек перебирал
семь стратегий, не зная, что цель может открываться и без них.

Теперь эталон идёт первым, и гоняется он **с полностью остановленным
ядром** (`id == "off"` → `StartCoreForTune` не вызывается), а не с
отключённым профилем: вопрос «блокируют ли» надо проверять так, как будто
программы нет. Если эталон прошёл — перебор прекращается.

**3. Одна попытка на цель.** `TryTlsProbe` вызывался ровно раз. Многие DPI
пропускают первое соединение и режут следующие — отсюда «подобрал, а не
работает». Теперь `ProbeTarget` делает три попытки с паузой 250 мс, счёт
успехов уходит в интерфейс. После двух неудач оставшиеся попытки
пропускаются: нужного счёта уже не набрать, а каждая неудачная проба стоит
целого таймаута.

**Заодно: сверка сертификата.** Раньше засчитывалось любое состоявшееся
рукопожатие, хотя завершить его может и промежуточное устройство со своим
сертификатом. `CertNameMatches` сверяет CN с запрошенным именем, нестрого
(wildcard и родительский домен), — полная проверка цепочки дала бы ложные
провалы на корпоративных машинах, а нас интересует только подмена
собеседника.

**Грабли, на которые едва не наступили.** Нативная часть переставляет
варианты (эталон вперёд), а интерфейс обновлял строки **по индексу**
(`i === data.index`). При любом расхождении порядка результаты легли бы не в
те строки. Переведено на сопоставление по `id`.

**Чего подбор по-прежнему не умеет:** проверяет установку соединения, но не
передачу данных. Блокировка в середине потока (случай друга пользователя,
§3) выглядит для него успехом. Следующий шаг — скачивание куска с
googlevideo и веб-сокет до gateway.discord.gg, плюс мастер первого запуска
поверх этого.

## 5г. Запланировано

### Обновления — СДЕЛАНО в v0.1.2

Репозиторий публичный с 2026-09-03. `checkForUpdates` сравнивает
`APP_VERSION` с `tag_name` последнего релиза, `DownloadAndApplyUpdate` в
`NativeApp.cs` качает, сверяет SHA-256 и подменяет exe через `apply_update.cmd`.

Что нельзя трогать, не сломав механизм:

* **Версия живёт в четырёх местах** — `build.ps1`, `AppVersion` в
  `NativeApp.cs`, `APP_VERSION` в `AppContext.tsx`, `version` в `package.json`.
  Разойдутся — проверка обновлений начнёт врать. `build.ps1` это проверяет и
  падает. В разметке версию писать нельзя вообще: в 0.1.3 нашлись ещё два
  зашитых места (заголовок окна и стартовая запись в логе), теперь оба берут
  `APP_VERSION`, а сборка ищет строки `v0.0.0-portable` и падает на них.
* **Установка без `SHA256SUMS.txt` не выполняется.** Мы запускаем скачанный
  exe с правами администратора, непроверенный файл здесь недопустим.
* **Ссылка проверяется** на github.com/githubusercontent.com: адрес приходит
  из интерфейса, и без проверки подменённая страница подсунула бы чужой файл.
* **`apply_update.cmd` пишется в ASCII, пути передаются через переменные
  окружения** `ZAPRET_UPDATE_SRC` и `ZAPRET_UPDATE_DST`. Так надо, и вот
  почему (проверено вживую 2026-09-05):
  `cmd.exe` разбирает .cmd в **OEM**-кодировке (866 на русской Windows), а
  `Encoding.Default` в .NET — это **ANSI** (1251). Это разные кодировки.
  Кириллический путь, записанный в 1251, читался как «╥хёЄ» вместо «Тест»,
  `copy` не находил цель, и обновление молча не ставилось. Окружение
  передаётся процессу в Unicode и от кодировок не зависит вообще —
  поэтому в скрипте не должно быть ни одного не-ASCII символа.
* **В скрипте нет `pause`.** Процесс запускается с `CreateNoWindow = true`,
  консоли нет, и `pause` в ветке `:fail` вешал невидимый `cmd.exe` навсегда.
  Причина сбоя пишется в `update\update-failed.log`.
* Пауза сделана через `ping`, а не `timeout`: последний требует консоли,
  а скрипт запускается скрытым. После успешной подмены скачанная сборка
  удаляется — иначе в `update\` копятся десятки мегабайт на каждое обновление.
* Имена ассетов фиксированы: `Zapret2-GUI-v<версия>-portable.exe` и
  `SHA256SUMS.txt`. Их создаёт `build.ps1`, заливает `publish_release.ps1`.


запись на этой машине. Файл лежит вне репозитория.

**Каталог отдельный от данных приложения, и это не косметика.** Раньше токен
лежал в `%LOCALAPPDATA%\Zapret2-GUI` рядом с `bin`, `dist` и журналами. При
разборе проблемы с настройками пользователь снёс этот каталог целиком — и
токен пропал вместе с ним, публикация 0.3.0 упала на «Токен не найден».
`save_release_token.ps1` переносит файл из старого места автоматически,
`publish_release.ps1` какое-то время смотрит в оба.

**Токен видеть нельзя и просить не надо.** Пользователь предлагал прислать его
в переписку — отказано: токен в чате остаётся там навсегда. Схема с DPAPI даёт
тот же результат, не показывая значение. `publish_release.ps1` расшифровывает

заголовки запроса вместе с `Authorization`.

**Публикация релиза требует подтверждения пользователя каждый раз.**
Договорённость от 2026-09-04: собрать, показать что вышло, опубликовать
только после явного «да». Действие публичное и необратимое.

### Антивирус: ложные срабатывания на нашу сборку

При публикации 0.1.4 Defender забраковал скачанный из релиза exe как
`Trojan:Win32/Wacatac.H!ml`. Суффикс `!ml` — вердикт машинного обучения, не
сигнатура. Сборка подходит под эвристику идеально: не подписана, распаковывает
из ресурсов драйвер и запускает его от администратора.

* **Это не находка в коде.** 0.1.2 и 0.1.3 из тех же исходников чистые,
  флагнута была именно 0.1.4. Вердикт цепляется к конкретному набору байт.
* **Пересборка НЕ лечит.** Сначала показалось, что лечит: пересобранный файл
  прошёл `MpCmdRun -Scan` и скачался без помех. Это была ложноотрицательная
  проверка — облачная модель ещё не оценила новый файл. Часа через два тот же
  файл `f841627222…` был заблокирован и при скачивании, и локально, а копию в
  рабочем дереве Defender удалил. **Свежесобранный файл нельзя считать чистым:
  вердикт приходит с задержкой.**
* **0.1.5 вердикта не получила.** Проверено 2026-09-10 в 09:29, через восемь
  часов после сборки: файл в рабочем дереве цел, `MpCmdRun -Scan` чист, в
  `Get-MpThreatDetection` последнее срабатывание относится к 0.1.4 (08.09).
  Окно задержки облачной модели пройдено с запасом. Вывод прежний: это
  лотерея на конкретный набор байт, а не свойство исходников.
* **Упаковка в архив тоже не помогает.** Defender проверяет содержимое: `.7z`
  со сборкой внутри был опознан так же (`containerfile:…7z->…exe`).
* **Проверять надо именно скачанный файл**, а не локальный: срабатывание
  происходит по метке «загружено из интернета». Порядок проверки — скачать
  ассет с GitHub и посчитать хэш; если файл не читается, его забрал антивирус.
* Ассеты в уже опубликованном релизе заменяются ключом
  `publish_release.ps1 -ReplaceAssets` (GitHub на повторное имя отвечает 422,
  поэтому старый ассет сначала удаляется).
* В апдейтере блокировка ловится отдельно (`ERROR_VIRUS_INFECTED` 0x800700E1
  и `ERROR_VIRUS_DELETED` 0x800700E2) и объясняется человеческим языком —
  иначе виден невнятный отказ в доступе к файлу.
* **Настоящее решение — подпись кода сертификатом.** Репутация тогда
  накапливается на издателя, а не на каждый файл. До этого — отправка ложного
  срабатывания вендорам на каждый релиз: порядок и готовые тексты в
  `docs/antivirus-false-positive.md`.
* Описание уже опубликованного релиза правится ключом
  `publish_release.ps1 -UpdateNotes` — берёт текст из `release-v<версия>/README.txt`
  и не трогает ассеты.
* **В исключения антивируса ничего не добавляем сами** — это изменение
  настроек безопасности, его делает пользователь и осознанно.

Две особенности `publish_release.ps1`, обе выяснились на публикации 0.1.3:

* **Ассеты заливаются с копии во временном каталоге.** `Invoke-RestMethod
  -InFile` открывает файл без разрешения на совместное чтение, поэтому
  запущенная сборка той же версии блокирует публикацию наглухо — а запустить
  её сразу после сборки как раз нормально. `Copy-Item` запущенный exe читает.
* **Существующий релиз не ошибка.** Если релиз уже создан, но ассетов нет
  (заливка упала на полпути), скрипт подхватывает его по тегу и доливает
  недостающее, сверяясь со списком уже загруженных имён. Удалять релиз и
  начинать заново не нужно.

Ядро zapret этим механизмом НЕ обновляется: winws.exe и WinDivert вшиты
ресурсами. Выход новой версии ядра отмечается отдельной строкой в логе.

## 5в-2. Автоподбор охватывает два профиля (0.1.5)

До 0.1.5 автоподбор проверял только `www.youtube.com` и `googlevideo.com` и
менял только профиль YouTube/Google. Профиль обычных сайтов — тот, через
который идут `discord.com`, `gateway.discord.gg` и `updates.discord.com`, —
не менялся ни в одном варианте.

**Это вводило в заблуждение**: человек с неработающим Discord видел
«пройдено 2 из 2» и считал, что подобрал настройку, хотя для Discord не
проверялось ничего. Выяснилось на логе пользователя, который перебрал шесть
вариантов подряд — все шесть командных строк для профиля 5 были одинаковыми.

Теперь у подбора две группы (`StrategyGroup` = `youtube` | `sites`), у каждой
свои цели и свой профиль. Группы независимы: у одного провайдера для YouTube
проходил seqovl, а для Discord — только `multidisorder` с разрезами
`1,midsld,host+1,sniext+1`.

* Умолчание профиля сайтов — `seqovl568`, ровно как было до 0.1.5, чтобы
  обновление не сломало работающие настройки.
* Нативную часть менять не пришлось: `RunAutotune` получает готовые командные
  строки и список хостов, так что группы — целиком забота интерфейса.
* **Позиция разреза важнее режима.** `--dpi-desync-split-pos=1` режет после
  первого байта и имя хоста не прячет — вся надежда на фейк `seqovl`. Прячут
  SNI маркеры `host+1` и `sniext+1`, которые режут внутри самого имени.
  Смена только режима (`multisplit` → `multidisorder`) при `split-pos=1`
  практически ничего не даёт.

## 5е. Уживание с чужими VPN и туннелями (0.2.4)

**Проблема, которую не видно в логе.** WinDivert перехватывает пакеты на
уровне IP, включая те, что идут В туннельный адаптер, то есть ещё НЕ
зашифрованные. Фильтр задавался только по портам, без привязки к интерфейсу,
поэтому при поднятом VPN winws резал содержимое чужого туннеля. Провайдер
внутри туннеля всё равно ничего не видит — пользы ноль, а сломать
подключение самого VPN можно.

**Ограничить фильтр можно только одним способом.** `--wf-raw-part`
складывается с портовым фильтром по **ИЛИ** (`wf_make_filter`, nfqws.c:1702)
и потому РАСШИРЯЕТ фильтр, а не сужает. Штатный способ — `--wf-iface=<idx>`:
он подставляется в начало через И (`ifIdx=%u and subIfIdx=%u and`).

**Какой индекс подставлять.** Физической карты, а не выходного интерфейса:
если выход идёт через туннель, ядро всё равно должно смотреть на реальную
карту. Отбор физической карты — тот же, что для проб автоподбора
(`FindPhysicalInterface`): настоящий MAC, нет опознаваемого слова в
описании, есть шлюз.

**Чем определяется реальный выход.** `GetBestInterfaceEx` из iphlpapi для
публичного адреса (1.1.1.1) — система сама отвечает, каким интерфейсом
пойдёт. Это точнее, чем перечислять поднятые адаптеры: поднятый, но
простаивающий туннель обходу не мешает.

Старый пункт проверки окружения («Активны виртуальные адаптеры: Tailscale.
Если через них уходит весь трафик...») перекладывал на человека вопрос, на
который может ответить система. Теперь пункт появляется, только когда выход
ДЕЙСТВИТЕЛЬНО идёт через туннель, и называет его по имени.

**Обратная сторона привязки — она fail-closed.** Сменилась карта (Wi-Fi
вместо кабеля, переподключение адаптера) — привязка указывает в никуда, и
обход продолжает считаться включённым, не видя ни одного пакета. Поэтому
нативная часть подписана на `NetworkChange.NetworkAddressChanged`, шлёт
интерфейсу новый маршрут, а тот при работающем ядре перезапускает его с
новой привязкой и пишет об этом в журнал.

**Проверено на машине пользователя:** `GetBestInterfaceEx(1.1.1.1)` вернул
`ifIndex=20` (Ethernet, не туннель), в команду подставляется
`--wf-iface=20`. Это тот же адрес `192.168.0.193`, с которого ручные пробы
дали честную картину блокировки, — см. §3, разбор 0.2.4 ниже.

**Про встраивание VPN в приложение (обсуждалось на 0.3.0).** Решено пока не
делать. Кратко: xray-core или sing-box это +30 МБ к сборке (сейчас 2,3 МБ)
плюс ~20 МБ баз geoip/geosite, второй драйвер (wintun) и гарантированные
срабатывания антивируса поверх нынешних. Лицензии: xray MPL-2.0, sing-box
GPL-3.0, а в репозитории файла лицензии нет вовсе. Отдельная ловушка:
REALITY-конфиги подставляют чужое имя в SNI, и если оно попадёт в наши
списки (`www.google.com` есть в list-google.txt), обход разрежет
рукопожатие самого VPN. `microsoft.com` и `nvidia.com` в list-exclude.txt,
эти безопасны.

## 5д. Оформление (0.1.4)

**Палитры Tailwind подменены на CSS-переменные.** Интерфейс написан обычными
классами: акцент — `indigo-*` (270 употреблений), поверхности и текст —
`slate-*` (603). Править их руками нельзя, поэтому в `tailwind.config.js` обе
палитры объявлены как `rgb(var(--accent-N) / <alpha-value>)`, а значения
ставит `src/lib/theme.ts` в `<html>`. Ни один компонент об этом не знает.

* Формат переменной — «R G B» без `rgb()`. Иначе перестанет работать
  модификатор прозрачности: `bg-indigo-600/20`.
* Значения по умолчанию лежат в `src/index.css`. Без них первый кадр
  рисуется вообще без цветов.
* **Поверхности тонируются только по тону и насыщенности.** Светлота каждой
  ступени остаётся ровно как у Tailwind, иначе первым же делом ломается
  контраст текста: `text-slate-900` на светлой теме и `text-slate-100` на
  тёмной держатся именно на светлоте. Проверено: при фоне «Графит» ряд
  совпадает со стандартным slate с точностью до 1-4 единиц на канал.
* Акценты заданы готовыми рядами Tailwind, а не выведены из тона: ряды,
  рассчитанные из чистого HSL, уходят в грязь на средних ступенях.
* Своя картинка: ужимается до 1600 px и живёт в localStorage (там около
  5 МБ на всё). Средний тон считается векторно — среднее арифметическое
  углов дало бы для 350° и 10° результат 180° вместо 0°.
* Ошибка, которую поймал тест при разработке: в подборе ближайшего акцента
  расстояние вычиталось из 180, и выбирался самый далёкий цвет.
  `|((a - b + 540) % 360) - 180|` — это уже расстояние по кругу.

**Зашитых цветов вида `bg-[#0F172A]` в разметке быть не должно.** Их было
шесть (боковая панель, рабочая область, заголовок окна, четыре диалога), и
они не следовали ни за темой, ни за выбранным фоном.

## 7. Грабли инструментов

* **`scripts/build.ps1` обязан быть UTF-8 с BOM.** PowerShell 5.1 без BOM
  калечит кириллицу.
* `Get-ChildItem "dir" -File -Exclude "*.txt"` возвращает пустоту, если в пути
  нет `\*`. В build.ps1 используется `Where-Object`.
* `.gitattributes` с `* -text` обязателен: иначе git переведёт в CRLF файлы
  списков, `.bin`-пейлоады и `build.ps1` вместе с его BOM.
* Имена ресурсов в `build.ps1` (`dist.zip`, `bin.zip`, `lists.zip`, три DLL
  WebView2) должны совпадать с тем, что читает `NativeApp.cs`.
* Патчить `src/**` и `NativeApp.cs` лучше скриптом из файла, а не heredoc'ом:
  экранирование `\r\n` внутри строковых литералов C# ломает компиляцию.

### Техдолг

* **Профиль 5: `seqovl=568` с 681-байтным паттерном.** Фейк получается
  обрезанной TLS-записью, у Flowseal для этого случая отдельный файл ровно на
  568 байт. Единственный пункт, способный сломать работающие сайты, поэтому
  делать отдельно и проверять автоподбором, а не на глаз.
* `stable.dl2.discordapp.net` в `list-google.txt` — см. §5a.
* Списки вшиты в exe и стареют; нужна кнопка обновления и дата.

### Не решено

* **YouTube.** Перебор стратегий у пользователя идёт через системный прокси,
  поэтому результаты могут ничего не значить — см. §5b. Автоподбор проверяет
  напрямую, мимо прокси, и это единственный достоверный источник.
* Почему `../host-list/...` не работает для winws, хотя работает для `mdig.exe`
  из той же сборки. Не блокирует — абсолютные пути решают.
